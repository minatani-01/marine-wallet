# NPB 公式サイト データ取得 調査結果

調査日: 2026-09-14
調査方法: Supabase (ap-northeast-1) から `http` 拡張で npb.jp に実接続し、返却された HTML を実測

本書は Marine Wallet の「試合記録の自動取得（Phase 2）」を実装するための、
npb.jp の実構造にもとづく仕様メモである。推測は含まない。すべて実取得で確認した。

---

## 1. 前提条件

### 1.1 robots.txt

`https://npb.jp/robots.txt` は **404（存在しない）**。
クロールを禁止する宣言は置かれていない。

ただし robots.txt の不在は「何をしてもよい」という意味ではない。
実装時は以下を守ること。

- 取得は 1 日 1 回（試合終了後の深夜〜早朝）に限定する
- 1 回の実行で取得するページ数は必要最小限にする
- 連続リクエストの間に 1 秒以上の間隔を空ける
- 個人利用の範囲にとどめ、取得データを再配布しない
- 著作権表示は `Nippon Professional Baseball Organization.` であり、
  ページ内容そのものの転載は行わない（自分の貯金額の算出にのみ使う）

### 1.2 User-Agent によるアクセス遮断（重要）

npb.jp は **ボット系の User-Agent を接続レベルで遮断する**。
TLS ハンドシェイク後に一方的に切断され、HTTP ステータスすら返らない。

実測結果:

| User-Agent | 結果 |
|---|---|
| `MarineWalletBot/0.1 (...)` | `SSL_ERROR_SYSCALL`（接続切断） |
| `Mozilla/5.0 (compatible; MarineWalletBot/0.1)` | `SSL_ERROR_SYSCALL`（接続切断） |
| `Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/140.0.0.0 Safari/537.36` | **200 OK** |

同一ネットワークから `example.com` は問題なく取得できたため、
これは npb.jp 側の挙動であってネットワーク側の問題ではない。

したがって実装では通常のブラウザ相当の UA と以下のヘッダーを送る必要がある。

```
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/140.0.0.0 Safari/537.36
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Accept-Language: ja,en-US;q=0.7,en;q=0.3
Upgrade-Insecure-Requests: 1
```

### 1.3 実行場所

Claude Code のクラウドセッションは egress プロキシ配下にあり npb.jp へ到達できない。
本番の取得処理は **Vercel のサーバーランタイム**（Cron + Route Handler）で実行する。
開発時の疎通確認も Vercel 側で行う。

## 2. 使えるページと取得できる項目

### 2.1 月別 試合日程・結果

```

```

`rowspan` で日付セルが省略される行でも取りこぼさない。

```html
<tr id="date0901" class="">
  <th rowspan="6">9/1（火）</th>
  <td>
    <div class="team1">ロッテ</div>
    <a href="/scores/2026/0901/m-l-20/">
      <div class="score1">1</div>
      <div class="state">-</div>
      <div class="score2">0</div>
    </a>
    <div class="team2">西武</div>
  </td>
  <td>
    <div class="place">ZOZOマリン</div>
    <div class="time">18:00</div>
    <div class="weather"> </div>
  </td>
  <td><div class="comment"></div></td>
  <td>
    <div class="pit">勝：高野脩</div>
    <div class="pit">敗：平良</div>
  </td>
</tr>
```

取得できる項目:

| 項目 | セレクタ | 備考 |
|---|---|---|
| 日付 | `tr` の `id` 属性（`dateMMDD`） | 年は URL 側から |
| ホーム球団 | `.team1` | NPB 表記では team1 がホーム |
| ビジター球団 | `.team2` | |
| ホーム得点 | `.score1` | 未実施は `&nbsp;` |
| ビジター得点 | `.score2` | 未実施は `&nbsp;` |
| 勝敗 | score1 と score2 の比較 | 同点は引き分け |
| 球場 | `.place` | |
| 開始時刻 | `.time` | |
| 中止・特記 | `.weather` / `.comment` | 中止はここに入る |
| 勝利／敗戦投手 | `.pit`（`勝：` `敗：` `分：` `先発：` 接頭辞） | 試合前は `先発：`（予告先発） |
| ボックススコア URL | `a[href^="/scores/"]` | 未実施の試合は存在しない |

未実施の試合も行として存在するため、**予定の先取りにも使える**。

実測（2026年9月・マリーンズ）: 終了 10 試合 + 予定 13 試合を正しく抽出できた。

### 2.3 チーム別 個人成績（シーズン累計）

```
https://npb.jp/bis/2026/stats/idb1_m.html   個人打撃（マリーンズ）
https://npb.jp/bis/2026/stats/idp1_m.html   個人投手（マリーンズ）
```

`<table class="tablefix2">`。ページ内に `2026年9月13日 現在` という基準日表記があり、
**前日終了時点のシーズン累計**である（当日の試合は未反映）。

打撃 23 列:

```
選手 / 試合 / 打席 / 打数 / 得点 / 安打 / 二塁打 / 三塁打 / 本塁打 / 塁打 / 打点 /
盗塁 / 盗塁刺 / 犠打 / 犠飛 / 四球 / 故意四 / 死球 / 三振 / 併殺打 / 打率 / 長打率 / 出塁率
```

投手 24 列:

```
選手 / 登板 / 勝利 / 敗北 / セーブ / ホールド / ＨＰ / 完投 / 完封勝 / 無四球 / 勝率 /
打者 / 投球回 / 安打 / 本塁打 / 四球 / 故意四 / 死球 / 三振 / 暴投 / ボーク / 失点 / 自責点 / 防御率
```

パース上の注意:

- 投球回は 2 つの span に分かれる
  `<td><span class="integer">15</span><span class="decimal">.1</span></td>` = 15回1/3
  `.1` は 1/3 回、`.2` は 2/3 回。三進法なので単純な小数として加算してはいけない
- 左投手・左打者の名前セルは `<td class="left-hand"><sup>*</sup>小島 和哉</td>` の形になる。
  `<sup>` を除去してから氏名を取る
- 氏名の姓名間は全角スペース

実測（2026-09-13 時点）: 打撃 59 名 / 投手 30 名。

## 3. 取得できないもの

**NPB 公式は 1 試合ごとの個人打撃成績（打数・安打・打点）を公開していない。**

ボックススコアページを精査したが、掲載されるのは
責任投手・バッテリー・本塁打・最新のオーダー（打順と守備位置のみ）であり、
選手別の成績行は存在しない。サブページへのリンクも無い
（ページ内の `/scores/` リンクは当日の他試合速報のみ）。

したがって、Marine Wallet の貯金ルールのうち
**打点・マルチ安打・QS は、ボックススコアからは直接取得できない。**

## 4. 個人成績を日次差分で求める方式

シーズン累計テーブルを毎日スナップショットし、その差分を「その日の成績」とみなす。
マリーンズは 1 日 1 試合であるため、差分はそのまま 1 試合の成績になる。

| 貯金ルール | 差分での判定 | 精度 |
|---|---|---|
| 打点 | `打点` の増分 | 正確 |
| マルチ安打 | `試合` の増分が 1 かつ `安打` の増分が 2 以上 | 正確 |
| QS | `登板` の増分が 1 かつ `投球回` の増分が 6 回以上かつ `自責点` の増分が 3 以下 | 正確 |
| 勝利投手 | ボックススコアの `【勝投手】` を直接使う | 正確 |
| セーブ | ボックススコアの `【セーブ】` を直接使う | 正確 |
| 完封 | `完封勝` の増分が 1 以上 | 正確 |
| 本塁打 | ボックススコアの本塁打欄を直接使う | 正確 |

### 4.1 この方式の制約

- **ダブルヘッダー**が組まれた日は差分が 2 試合分に混ざる。
  `試合` の増分が 2 の場合はマルチ安打判定を保留し、手動確認に回す
- **取りこぼすと復旧できない。** スナップショットを 1 日飛ばすと、
  その日の差分と翌日の差分が合算されてしまう。
  対策として、スナップショットには基準日（`2026年9月13日 現在`）を必ず保存し、
  前回スナップショットとの基準日の差が 1 日を超えた場合は
  その区間を「自動確定しない」として手動入力に回す
- **シーズン開始時**は前スナップショットが無いため、初回は差分ゼロとして扱う
- 選手の識別は氏名文字列に依存する。同姓の登録名（例: `佐藤`）が重複しうるため、
  可能ならボックススコア側の選手 ID と突き合わせる

### 4.2 必要なテーブル

```
npb_player_stat_snapshots
  id                 uuid primary key
  as_of              date not null          -- ページ記載の「YYYY年M月D日 現在」
  kind               text not null          -- 'batting' | 'pitching'
  player_name        text not null
  stats              jsonb not null         -- 列名 -> 数値
  fetched_at         timestamptz not null default now()
  unique (as_of, kind, player_name)

npb_games
  id                 uuid primary key
  game_date          date not null
  home_team          text not null
  away_team          text not null
  home_score         int
  away_score         int
  place              text
  phase              text                   -- 公式戦 / CS / 日本シリーズ
  win_pitcher        text
  lose_pitcher       text
  save_pitcher       text
  box_score_path     text
  status             text not null          -- scheduled | finished | cancelled
  unique (game_date, home_team, away_team)
```

既存の `games` テーブルには、検証が済んだうえで反映する。
自動取得はまず `npb_games` に貯め、内容を確認してから `games` に取り込む二段構えにする。

## 5. 実装方針

### 5.1 実行基盤

Vercel Cron（Hobby プランは 1 日 1 回まで）で
`/api/cron/npb-sync` を日本時間 05:00（UTC 20:00）に実行する。

`vercel.json`:

```json
{
  "crons": [
    { "path": "/api/cron/npb-sync", "schedule": "0 20 * * *" }
  ]
}
```

Route Handler は `CRON_SECRET` を検証してから実行する。

### 5.2 1 回の実行で取得するページ

1. 当月の日程・結果ページ（1 ページ）
2. 前日に試合があった場合、そのボックススコア（最大 1 ページ）
3. 個人打撃成績（1 ページ）
4. 個人投手成績（1 ページ）

合計 4 ページ。各リクエストの間に 1 秒のウェイトを入れる。

### 5.3 実装順序

1. `npb_player_stat_snapshots` / `npb_games` のマイグレーション（0021 で適用済み）
2. パーサーを純関数として実装し、ユニットテストを書く（`lib/npb/` に実装済み）
3. Route Handler と Cron を追加し、まず「取得して貯めるだけ」で動かす（実装済み・未稼働）
4. 数日分たまったら差分計算の結果を既存の手入力データと突き合わせて検証
5. 検証が通ったら `games` への自動反映と貯金エントリ生成をつなぐ

### 5.4 稼働させるのに必要な設定

Vercel のプロジェクト設定で、次の2つの環境変数を追加する。
どちらも `NEXT_PUBLIC_` を付けない（ブラウザに渡ってはいけない）。

| 変数名 | 値 |
|---|---|
| `CRON_SECRET` | 任意の長い文字列。Vercel Cron が `Authorization: Bearer <値>` で送る |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase の service_role キー |

`SUPABASE_SERVICE_ROLE_KEY` は RLS を迂回する。リポジトリは公開なので、
コードにも `.env` にも書かず、Vercel のダッシュボードで直接入力する。

設定が終わるまで Cron は 500 を返して何も保存しない。
手で動作を確かめるときは次のようにする。

```
curl -H "Authorization: Bearer <CRON_SECRET>" \
  https://marine-wallet.vercel.app/api/cron/npb-sync
```

実行の記録は `npb_sync_runs` に残る。`ok` と `summary`（取得ページ数・
保存件数・スナップショットの基準日・警告）を見れば、
取得が飛んだ日や構造の変化に気づける。

### 5.5 実装上の注意

- **Middleware を通さないこと**。`proxy.ts` の認証ガードは全リクエストを通るため、
  `/api/cron/` を除外しないと Cron がログイン画面へリダイレクトされて実行できない。
  代わりに Route Handler 側で `CRON_SECRET` を確かめる
- **パラメータプロパティを使わないこと**。Node の型ストリップが未対応で、
  `node:test` から読み込めなくなる

## 6. アプリ側の対応（2026-09-14 反映済み）

本調査の結果を受けて、貯金の登録手段を次のとおり整理した。

| 画面 | 旧名称 | 新名称 | 役割 |
|---|---|---|---|
| 貯金タブ | 試合登録 | **自動登録** | npb.jp から取得できる項目だけを扱う |
| 貯金タブ | カスタム貯金 | **カスタム登録** | 自動取得できない分を任意額で積み立てる |

自動登録が扱うのは NPB 公式から取得できる項目だけにした。
取得できないものはカスタム登録へ移した。

| 項目 | 取得 | 根拠 |
|---|---|---|
| 日付・対戦相手・ホーム/ビジター・球場 | 可 | 日程・結果ページ |
| フェーズ | 可 | ボックススコアの h3 の【...】 |
| 勝敗・スコア | 可 | 日程・結果ページ |
| ホームラン・満塁ホームラン | 可 | ボックススコアの本塁打欄 |
| 勝利投手・セーブ | 可 | ボックススコアの責任投手欄 |
| 完投・完封 | 可 | 個人投手成績の「完投」「完封勝」列の差分 |
| マルチ安打・打点 | 不可 | 1試合ごとの個人打撃成績が非公開 |
| サヨナラ勝利 | 不可 | 推定はできるが公式に項目が無い |
| ノーヒットノーラン・完全試合 | 不可 | 該当する列が無い |
| その他ボーナス（珍記録） | 不可 | 自由記述 |

自動登録から削除した入力欄:

- マルチ安打・打点
- サヨナラ勝利
- その他ボーナス（珍記録）
- 投手ボーナスの選択肢のうち ノーヒットノーラン・完全試合・QS

投手ボーナスは **なし / 完投 / 完封** の3つになった。
QS は累計差分から求められるが、貯金の対象にしないため外した。

ノーヒットノーランは「完投+1 かつ安打の増分が0」で導出できなくはないが、
スナップショットを1日取りこぼすと判定が崩れる。
年に数回あるかないかの記録のために壊れやすい推定は入れない。

カスタム登録には**定型**のプルダウンを置いた。
選ぶとその名前と金額が入る。決まった金額が無い珍記録などは直接入力する。

定型は `saving_custom_presets` テーブルの行で、貯金ルールの画面から
追加・金額変更・削除ができる（0022のマイグレーション）。
NPB から取得できない記録は人によって増えるため、アプリに直書きしない。
初期値としてサヨナラ勝利・ノーヒットノーラン・完全試合を入れてある。

読み取りはログイン中の全員、変更できるのは貯金ルールを変更できる人だけ
（`can_edit_saving_rules`）。ルール本体の「保存する」とは別に、
定型はその場で反映する。追加したのに保存を押し忘れる事故を避けるため。

貯金ルール画面は、自動登録で使わなくなった単価を整理した。
マルチ安打・打点・QS は設定しても効かないので外した。
サヨナラ勝利・ノーヒットノーラン・完全試合の金額は定型が持つようになったので、
単価の一覧からは外している。

`saving_rule_settings` の `sayonara_bonus` / `no_hitter_amount` /
`perfect_game_amount` は列として残している。過去に自動登録で記録した試合を
編集したときに `calcSaving` が参照するため、消すと過去の金額が変わってしまう。
画面から触れなくなるので、値はこの時点で固定される。

### UI

1項目で3行使う作りだったため、シートが縦に長くなっていた。
自動登録は将来 NPB から自動で埋める想定なので、手で触る面積を小さくした。

- 対戦相手の11個のチップ（4行）をプルダウン1行に
- フェーズの4個のチップをプルダウンにし、倍率は選択肢の中に
- 試合結果のチップを Segmented にして1行に
- カウンターとスイッチを、ラベルと操作が1行に収まる形に

カスタム登録は全項目が1画面に収まるようになった。

過去に手入力された試合の `multi_hits` / `rbi` は DB に残したままで、
`calcSaving` の計算ロジックも残している。
GameSheet も読み込んだ値をそのまま保存し直すので、
既存の試合を編集しても過去の金額は書き換わらない。

## 7. 単価について

自動取得を有効にすると、これまで手入力では拾いきれていなかった
QS などが漏れなく計上される。

現行の単価のままだと年間の積立額が
実績の約 54,600 円から増加する見込みである。
単価は運用しながら手動で見直す。

## 7. 貯金への取り込み（2026-09-16 反映）

取得した `npb_games` のうち、**前日に終わった1試合だけ**を `games` へ入れる
（`lib/npb/import.ts` / `lib/npb/register.ts`）。

積立はアプリ側では作らない。`games` に行が入ると DB のトリガー
（`games_sync_saving_entries` → `sync_saving_entries_for_game`）が対象者ぶんを
まとめて作る。金額の計算を2か所に置くと必ず食い違うので、試合を入れるところで
手を止めている。

### 7.1 前日分だけにする理由

過去分をまとめて作り直すと、想定しない書き換えが起きたときに追えなくなる。
毎朝1試合だけを見て、**追加しかしない**。すでに `games` にその日の試合が
あれば、手で登録したものか編集したものなので何もしない。積立も
`ignoreDuplicates` で入れるので、手で直した金額を翌朝戻すことはない。

### 7.2 自動で埋める項目

| 項目 | 取得元 |
|---|---|
| 勝敗・得点 | 日程表のスコア |
| ホーム / ビジター | 日程表の並び（ロッテがホーム側か） |
| 対戦相手 | 日程表の球団名。`OPPONENTS` に無い名前なら取り込まない |
| 本塁打・満塁本塁打 | ボックススコアの本塁打欄。自軍ぶんだけ数える |
| セーブ | ボックススコアの【セーブ】。勝った試合のみ |
| フェーズ | ボックススコアの h3【...】 |

### 7.3 自動では埋めない項目

いずれも npb.jp の公開範囲では確かめられないため、既定値のままにする。
必要なら画面から手で直す。

| 項目 | 理由 |
|---|---|
| サヨナラ勝ち | イニング別得点を取っていない |
| 完封・完投などの投手記録 | 投球回が要る。ボックススコアから取っていない |
| 勝利投手 | 勝てば必ず自軍から出るので、入れると全勝利に上乗せが付く。手入力の53勝では1度も使っていない |
| マルチ安打・打点 | 個人別の打撃成績を NPB 公式が公開していない（3章） |

### 7.4 取り込まない場合

次のときは作らず、理由を `npb_sync_runs.summary.registered.reason` に残す。

| 理由 | 知らせるか |
|---|---|
| 前日に試合がない / 中止で得点が入っていない | 送らない（普通のこと） |
| すでに `games` に登録されている | 送らない（普通のこと） |
| ボックススコアを取得できていない | **送る**（0本で確定させないため見送る） |
| 対戦相手を判別できない / 1日に2試合ある | **送る** |

知らせるものは「試合を取り込めませんでした。貯金タブから手で登録して
ください」という通知になる。黙って見送ると、その日の貯金が抜けたことに
気付けないため。

### 7.5 取りこぼしの拾い直し

毎朝の取り込みは前日の1試合だけなので、仕組みを作る前に終わった試合や、
取り込みに失敗した試合は残る。これを拾うために、貯金タブの自動登録の中に
**マスターだけが押せる**「未登録の試合をまとめて取り込む」を置いた
（`lib/npb/backfill.ts` / `app/api/games/backfill/route.ts`）。

`npb_games` にあって `games` に無い終了済みの試合を、古い順に取り込む。
ボックススコアは1試合につき1ページ取りに行くので、間隔を空け、
1回あたり10試合までにしている。残りは返り値の `remaining` で分かるので、
0になるまで押せばよい。

毎朝の取り込みと同じで追加しかしない。すでに `games` にある試合には触らない。

npb.jp へ出られるのは本番のサーバーだけなので、取得はサーバー側で行う
（開発環境や Supabase のDBからは接続を切られる）。

### 7.6 既知の制約

`npb_games` の `raw.box` は、その実行で最後に終わっていた1試合にしか入らない。
毎回すべての試合を upsert するので、前日より古い試合のボックススコアは
上書きで消える。前日分しか取り込まないので運用上は問題ないが、
過去に遡って取り込むことはできない。

## 8. 記録達成の取り込み

### 8.1 対象のページ

| 種類 | URL | 用途 |
|---|---|---|
| `milestone_batting` | `/history/<年>/milestones_b.html` | 達成が予想される記録（打撃） |
| `milestone_pitching` | `/history/<年>/milestones_p.html` | 同（投手） |
| `milestone_team` | `/history/<年>/milestones_team.html` | 同（チーム） |
| `roster` | `/bis/teams/rst_m.html` | 選手名鑑。背番号を引くため |

記録のページは年ごとにURLが変わる。名鑑は年で分かれず、常に今の登録選手が出る。

シーズン記録はこれらのページに載らない（どれも通算記録のページ）。
4章の個人成績スナップショット（`npb_player_stat_snapshots`）から拾う。

### 8.2 記録ページの作り（実物で確認済み）

記録ごとに `<h4>1000試合出場（過去541人）</h4>` があり、その下に**表が2つ**並ぶ。

| 表 | 列 |
|---|---|
| 達成済み | `氏名 / 所属 / 達成日 / 相手 / 回戦 / 球場 / … / 備考` |
| これから | `氏名 / 所属 / 昨年まで / 達成まで / 初◯◯ / …` |

**達成済みの表に達成日が入る**ので、前日と比べなくても達成が分かる。
「これから」の表では、達成すると `達成まで` が
`<span class="red">達成</span>` に変わる。

チームのページは `チーム / …`（球団名は「千葉ロッテマリーンズ」）。

#### 拾い間違いに注意

「ロッテ」は所属以外の欄にも出る。**所属の列だけ**を見ること。

| 紛らわしい例 | 中身 |
|---|---|
| 相手 | 牧原 大成（ソフトバンク）が「相手：ロッテ」で達成 |
| 当時の所属 | 鈴木 大地は現在楽天、当時の所属がロッテ |

### 8.3 いまの流れ

毎朝の取り込み（`/api/cron/npb-sync`）が、試合を入れたあとに続けて走る。
マスターは貯金タブの「記録達成を取り込む」からいつでも動かせる
（`/api/npb/milestones`）。

1. 4ページを取って `npb_source_pages` に置く（`lib/npb/pages.ts`）
2. 読み取って `npb_milestones` に入れる（`lib/npb/milestone-register.ts`）
3. `npb_milestones` のトリガーが、対象者ぶんの積立を作る

金額の計算を2か所に置かないよう、積立を作るのは DB 側に寄せてある。
試合のとき（`games_sync_saving_entries`）と同じ形。

取り込みに失敗しても試合の登録は止めない。空の中身は保存しない
（取れたことにして空を置くと、解析側が「記録なし」と読んでしまう）。

### 8.4 登録する形

自動登録として入れる。定型は記録の重みで3つに分けてある（0031 / 0033）。

| 定型 | 対象 | 金額 |
|---|---|---|
| 名球会記録 | 通算2000安打 / 200勝 / 250セーブ | 3,000 |
| 生涯記録 | それ以外の通算記録。チーム記録もここ | 1,000 |
| シーズン記録 | その年だけの記録（シーズン30本塁打 など） | 1,000 |

金額は定型が持つので、貯金ルールの「記録達成の金額」から変えられる。
この3つは `saving_custom_presets.auto = true` を立ててあり、
カスタム登録のプルダウンには出ない（自動で入るものを手でも入れないため）。

内容は `#背番号姓 通算◯◯記念` の形（例: `#52益田 通算250セーブ記念`）。
背番号は記録のページに無いので名鑑から引く。引けなければ `#` を付けない。
チーム記録は `マリーンズ 5000敗記念`。

### 8.5 同じ記録を二度入れない

`npb_milestones` の一意キー `(season, source, record_label, holder)` で防ぐ。
通算記録は一生に一度なので季を跨いでも重ならず、シーズン記録は
年が変われば改めて達成しうるので `season` を含めてある。

積立の側でも、同じ内容（`other_note`）で始まる行があれば作らない。
台帳を作り直したときの保険。

### 8.6 積立は必ず達成した月へ入れる

記録は「その月の出来事」なので、8月の達成は8月の行に並べる。

ただし、その月がもう確定・入金済みだと、積立を足しても累計に入らない
（累計は確定額を足すため）。そこで、確定済み・入金済みの月に足したときは
**確定額も同じだけ上げる**。月別も累計も食い違わなくなる。

| その月の状態 | 確定額 |
|---|---|
| 確定前（calculating） | 触らない。確定のときに集計しなおす |
| 確定済み（ready） | 積立の額を足す |
| 入金済み（deposited） | 積立の額を足す |

入金済みの月の確定額が上がると、その差額はまだワンバンクへ入れていない
ことになる。金額が宙に浮くよりは、足りていないと分かるほうがよい。

### 8.7 シーズン記録の節目

通算記録のページには載らないので、こちらで決めている
（`SEASON_THRESHOLDS`）。

| 打撃 | 投手 |
|---|---|
| 本塁打 30 / 40 / 50 | 勝利 15 / 20 |
| 打点 100 | セーブ 30 / 40 |
| 安打 150 / 200 | ホールド 30 / 40 |
| 盗塁 30 / 50 | 奪三振 150 / 200 |

達成日は個人成績ページの基準日にする。NPB は1試合ごとの個人成績を
公開しておらず、何日に届いたかは分からない。基準日は前日終了時点なので、
遅くともその日には届いている。

過去のスナップショットを古い順に見て、**節目を初めて越えた日**を採る。
最新の1日だけを見ると、仕組みを足す前に越えていた記録が「今日の達成」に
なってしまい、月がずれるため。

### 8.8 まもなく達成する記録（ホームのカウントダウン）

「これから」の表から、マリーンズの選手の残りを数えて
`npb_upcoming_milestones` に置く。ホームで近いものから3件出す。

**ページの「達成まで」は使わない。** あれは 目標 − 昨年まで で、今季ぶんが
入っていない（達成すると「達成」に変わるだけ）。そのままだと開幕直後の
数字を出し続けることになるので、昨年までの数に今季の成績を足して数え直す。

    あと8日   田村 龍弘   990（昨年まで）+ 2（今季）= 992

「あと◯◯」の単位は記録名のままだと読みにくいものがある。試合に出ることは
1日1試合なので、試合出場だけ「日」で数える（`countdownUnit`）。

今季の成績を引けない選手（その年に出場が無く、成績ページに行が無い）は
昨年までの数で数える。実際より遠くに出るだけなので、近いと嘘をつくことはない。

投球回は対象から外している。記録のページの「昨年まで」が `989.1` のような
三進法の小数で、成績のほうはアウト数。単位を揃える手間に見合わない。

その年の残りを出すものなので履歴は持たない。取り込みのたびに、その季のぶんを
消してから入れ直す。

## 9. すでに登録した試合の直し

手で入れた試合には、ホーム・ビジターや得点が入っていないものがある。
貯金タブの「未登録の試合をまとめて取り込む」（`/api/games/backfill`）が、
取り込みの前に直しまで行う。

1. `games` に試合があるのに取得データが無い月の日程・結果を取る（1回3か月まで）
2. ボックススコアをまだ取っていない試合を取る（1回8試合まで）
3. すでにある試合の、金額に関わらない項目を直す
4. まだ登録していない試合を取り込む

2 は取得データ（`npb_games`）に貯めるだけで `games` には触らない。
日程・結果のページには本塁打もセーブ投手も載らないので、金額に関わる項目を
npb.jp と突き合わせるには1試合ごとのボックススコアが要る。

### 9.1 直すものと直さないもの

| | 項目 |
|---|---|
| 直す | 対戦相手 / ホーム・ビジター / 球場 / 自軍の得点 / 相手の得点 |
| 直さない | 勝敗 / フェーズ / 本塁打 / 投手の記録 / その他ボーナス |

**この操作で金額は動かない。** 勝敗・本塁打・セーブは金額そのものなので、
取得データと食い違っていても書き換えず、件数を知らせるだけにする。
どれを直すかは人が決める。

本塁打とセーブはボックススコアを取っている試合だけ比べられる。
取っていない試合は比べない（0本として扱うと、静かに食い違いを作るため）。

フェーズは比べることすらしない。日程表にフェーズは載らず、ボックススコアを
見ないと分からない。一律 `regular` で入るので、比べると交流戦を
塗り替えてしまう。

### 9.2 直さない場合

| 見送る理由 | 中身 |
|---|---|
| 取得データがありません | その月をまだ取っていない。もう一度押せば取りに行く |
| 同じ日に複数の試合があります | どちらの試合か決められない。取り違えると別の試合を書く |
| 得点が入っていません | 中止・延期 |
